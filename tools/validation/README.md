# Validation artifacts

`validation/profiles/hbm2_2000.json` is the machine-readable V0.2 profile contract. It names the request format, organization, timing, mapping bits, each tool binding, and the remaining non-equivalence explicitly. `generate_microtraces.py` creates deterministic transaction CSVs. `summarize_hbmsim.py` runs the HBMSim binary with `--profile hbm2_2000`, saves each completion stream, and emits `validation/results/hbmsim-summary.csv` with request count, mean/p95 latency, and throughput.

The GitHub Actions workflow converts the same neutral CSV sequence for Ramulator 2.1 and DRAMSys, runs all three tools, and uploads `validation/` as `hbm-validation-results`. The entry point is `validation/results/three-simulator-comparison.csv`; raw Ramulator JSON statistics, DRAMSys TDB databases/logs, converted inputs, and configuration metadata are kept beside it for audit.

V0.3 uses one 32 B HBM2 pseudo-channel payload per request and absolute 1 ns arrivals. The reference workflow applies `patch_ramulator_timed_trace.py` only to the pinned checkout: it preserves those arrivals, waits for every read/write callback, and records per-request completion cycles. The comparison includes completion counts, mean/p50/p95 latency, throughput, ACT/PRE/RD/WR totals and row locality. The frozen baseline is [GitHub Actions run 34081337722](https://github.com/litao1991/hbmsim/actions/runs/34081337722). The manifest still records the HBM2 SID and DRAMSys stock-spec density/topology differences, so the results remain an auditable alignment baseline rather than a claim of bit-for-bit equivalence.

`assert_h6_gate.py` is the permanent CI acceptance gate. It verifies that every normalized trace is present in all three summaries and that each simulator accepted and completed exactly the input request count. It intentionally does not impose a latency-equality threshold: the comparison table exposes behavioural/model differences for review instead of converting them into a misleading strict-equivalence assertion.
